⏺ Assessment: how easy would it be?

  TL;DR — moderate but well-bounded. The architecture is already prepared for
  "two roles per database" (slot host + writer for pg_logical_emit_message),
  thanks to PR #1414. Adding a third role — read replica for SELECTs — is a
  clean extension. Probably ~1–2 days of work plus tests/docs.

  What the existing replica feature actually is

  Despite the issue title, the existing model isn't really
  physical-replica-only. PostgresDatabase has an embedded primary field, and the
   design assumes:

  - main connection (postgres_database) = where the slot lives + where SELECTs
  run
  - primary = fallback used only for pg_logical_emit_message (heartbeats +
  watermarks), since WAL-writing functions can't run on standbys

  It works for both PG16+ logical-decoding-on-standby and the docker example
  using a logical subscriber as the "replica"
  (docker/replica-cdc-dev/init-replica.sh).

  Your case is the inverse

  For Aurora logical replication you want: slot on primary (already works, no
  primary embed needed), SELECTs on a reader endpoint. Today, SELECTs always use
   the slot-hosting DB.

  What changes are needed

  1. Schema — add a read_replica embed to PostgresDatabase mirroring
  PostgresDatabasePrimary (lib/sequin/databases/postgres_database.ex:60,
  postgres_database_primary.ex). Migration is a single jsonb column.
  2. Split with_watermark/5 — lib/sequin/runtime/table_reader.ex:129. Currently
  the SELECT and the pg_logical_emit_message + pg_current_wal_lsn() calls share
  one connection. We'd need: SELECT on replica conn → emit watermark + fetch LSN
   on primary conn. The order (SELECT first, watermark after) is already correct
   for consistency.
  3. Route SELECTs to the replica in TableReaderServer —
  lib/sequin/runtime/table_reader_server.ex:376 (the fetch_batch_pks task) and
  :471 (the with_watermark wrapper). Add a helper like read_database(state)
  returning the replica DB or falling back to the main DB. Same pattern as
  slot_processor_server.ex:791 get_primary_conn/1. Apply to fast_count_estimate
  and fetch_first_row too.
  4. ConnectionCache — already keyed by db.id. Must give the replica a synthetic
   ID like "replicaof-#{db.id}" to avoid aliasing, mirroring
  slot_processor_server.ex:92.
  5. Plumbing — YAML loader, DB form, API controller, transforms.ex, docs.
  Mostly mechanical.

  Correctness story (this is the part to think hardest about)

  The watermark protocol still works. With SELECT on replica then watermark on
  primary:

  - SELECT sees replica snapshot at replica_lsn
  - Watermark emitted on primary at primary_lsn ≥ replica_lsn
  - Slot stream is LSN-ordered, so when the watermark message arrives, all CDC
  events with LSN ≤ primary_lsn (including everything between replica_lsn and
  primary_lsn) have already been processed
  - The existing pks_seen dedup (message_handler.ex:88,
  table_reader_server.ex:120) drops PKs from the in-flight batch when a CDC
  event arrives — so any row updated between replica_lsn and primary_lsn is
  dropped from the SELECT batch and delivered via CDC instead

  Net: no dups, no losses, even with replica lag. Aurora's <100ms lag is a
  non-issue; even seconds of lag is correct, just means more pks_seen work.

  Risks / things to verify

  - The dev fixture in docker/replica-cdc-dev/ is logical-subscription, not
  Aurora-style reader endpoint. Worth setting up an Aurora-flavored test (or
  LocalStack) before claiming production support.
  - Schema introspection (table OIDs) happens via the main DB. If the replica's
  OIDs differ (they shouldn't on Aurora; can on a logical subscriber),
  fetch_batch could break. Worth a sanity check at backfill start.
  - Must document that the slot-hosting DB user only needs SELECT on tables for
  initial introspection now; bulk SELECTs go through the replica user.

  Want me to take a stab at a draft PR? I'd start with the with_watermark
  refactor and a unit test, since that's the load-bearing change — everything
  else is plumbing around it.

❯ what happens if there's a backfill happening while new updates are being      
  sent? say theres a DELETE action from postgres, then the backfill re-adds the 
   document to typesense, is that possible?                                     

⏺ No — Sequin's watermark + pks_seen protocol prevents that exact scenario.
  Here's the flow for "row exists, backfill picks it up, then DELETE happens":

  T1: backfill SELECTs R2 → R2 added to batch X's pk_multiset
  T2: writer-side: pg_logical_emit_message (watermark X) at LSN_W
  T3: DELETE on R2 at LSN_D  (could happen anywhere relative to T1/T2)
  T4: slot stream delivers events in LSN order
  T5: slot processor flush — drops PKs already CDC'd

  The key invariant is in lib/sequin/runtime/table_reader_server.ex:120
  (pks_seen/2) plus lib/sequin/runtime/message_handler.ex:131 (the watermark
  handler that calls flush_batch). When a CDC event for R2 arrives, pks_seen
  removes R2 from every in-flight batch's multiset. When the watermark for batch
   X eventually arrives in the slot stream — which is LSN-ordered, so it can't
  arrive before any event with LSN < watermark_lsn — flush_batch filters the
  batch by what's still in the multiset. R2 is gone.

  Concretely for your DELETE scenario:

  When does DELETE happen: Before T1 (and replica caught up)
  What sink sees: SELECT misses R2 → only DELETE from CDC
  ────────────────────────────────────────
  When does DELETE happen: Before T1 (replica lagging, sees R2)
  What sink sees: SELECT picks R2, but DELETE is in slot stream < watermark_X,
    pks_seen drops R2, flush has no R2 → only DELETE
  ────────────────────────────────────────
  When does DELETE happen: Between T1 and T2
  What sink sees: DELETE is in slot stream < watermark_X, pks_seen drops R2 →
    only DELETE
  ────────────────────────────────────────
  When does DELETE happen: After T2 (LSN_D > LSN_W)
  What sink sees: Backfill flushes :read first, CDC DELETE arrives later → sink
    applies in order: write then delete

  In every case the final sink state matches Postgres. No resurrection.

  Two caveats worth knowing:

  1. Duplicate inserts are possible (and benign for Typesense). If a row is
  INSERTed after the backfill cursor passes its keyspace, no problem. If it's
  INSERTed in a keyspace the cursor hasn't reached yet, both the CDC INSERT and
  the eventual backfill :read will be delivered. Typesense upserts on PK so the
  doc is the same either way. But the message count is 2.
  2. Read-replica lag doesn't break this protocol — that's why I'm emphatic the
  watermark must be emitted on the writer, not the replica. The watermark's
  LSN_W is pg_current_wal_lsn() on the writer, which is necessarily ≥ any LSN_D
  of writes already committed on the writer. Any CDC event with LSN_D < LSN_W
  reaches the slot processor before the watermark, and pks_seen runs first. This
   is preserved in the split with_watermark/7 I added — watermark_db is always
  the writer, only the SELECT is on the replica.

  Where it could go wrong (none of which are normal operation):

  - If the slot processor is dead/stuck and never delivers the watermark, the
  batch sits in unflushed_batches. The :check_state timer detects this via the
  stale_batch check (table_reader_server.ex:705) and stops the reader instead of
   flushing — refusing to deliver beats delivering wrong.
  - If you bypass Sequin and write directly to Typesense out-of-band, all bets
  are off.
  - If you change the replication_slot_id mid-backfill (e.g., recreate the
  slot), the watermark message in WAL won't match the new slot's context filter
  and pks_seen won't run for the stuck batch. Don't do that.

  Short answer: yes, this is exactly the case the protocol was designed to
  handle, and the read-replica path preserves it.
